# 04 — Money logic (สเปกบังคับ)

เอกสารนี้คือ single source of truth ของทุกอย่างที่เกี่ยวกับตัวเลขเงิน **ห้ามเขียน logic การเงินโดยไม่อ้างอิงเอกสารนี้** โค้ดที่ implement แล้วอยู่ใน `core/domain/src/main/kotlin/com/triptogether/core/domain/` และเทสต์อยู่ใน `core/domain/src/test/kotlin/com/triptogether/core/domain/`

---

## 1. หน่วยเงิน

- เก็บและคำนวณเป็น **`Long` หน่วยสตางค์** เสมอ
- แปลงเป็นบาทเฉพาะตอนแสดงผลเท่านั้น
- ห้ามมี `Double` หรือ `Float` แตะจำนวนเงินแม้แต่ในตัวแปรชั่วคราว

```
1,850.00 บาท  →  185000L
0.01 บาท      →  1L
```

**เหตุผล:** `0.1 + 0.2` ใน floating point ได้ `0.30000000000000004` เมื่อสะสมข้าม 30 บิลในทริป ยอดรวมจะเพี้ยนหลักสตางค์ แล้ว invariant `sum(shares) == total` จะพังแบบสุ่ม ซึ่ง debug ยากมาก

---

## 2. โหมดการหาร

### 2.1 `EQUAL` — หารเท่า

หาร `totalAmount` ให้คนที่ถูกเลือก N คน

```
base      = total / n        (integer division)
remainder = total % n
```

`remainder` สตางค์ ถูกแจกคนละ 1 สตางค์ให้ **N คนแรกตามลำดับที่กำหนดใน §2.4**

ตัวอย่าง: 100.00 บาท / 3 คน → `10000 / 3 = 3333`, เหลือ `1`
→ `[3334, 3333, 3333]` รวม = `10000` ✓

### 2.2 `EXACT` — ใส่ยอดเอง

ผู้ใช้กรอกยอดของแต่ละคนเอง ระบบไม่คำนวณให้ แต่ **บังคับ validate**:

```
sum(shares) == totalAmount
```

ถ้าไม่ตรง → แสดงส่วนต่างและปิดปุ่มบันทึก ห้าม auto-correct เงียบ ๆ

ปุ่มช่วย 2 ตัวในหน้า editor:
- **"เกลี่ยส่วนที่เหลือ"** — เอา `total - sum(shares ที่กรอกแล้ว)` ไปหารเท่าให้คนที่ยังไม่กรอก (ใช้กติกา §2.1) ถ้าทุกคนกรอกครบแล้วปุ่มนี้ disable
- **"+ ค่าบริการ X%"** — เปอร์เซ็นต์เก็บเป็น **basis points จำนวนเต็ม** (10% = 1000 bp) ห้ามใช้ทศนิยม คำนวณ `newTotal = sum(shares) × (10000 + bp) / 10000` (integer division ทั้งหมด) แล้วกระจาย `newTotal` กลับให้แต่ละคนตามสัดส่วนเดิมด้วย largest remainder method (กติกาเดียวกับ §2.3 + ลำดับ §2.4) จากนั้นปรับ `totalAmount` เป็น `newTotal`

### 2.3 `SHARES` — หารตามสัดส่วน (weight)

แต่ละคนมี `weight` เป็นจำนวนเต็ม เช่น คนกินเยอะได้ 2 คนกินน้อยได้ 1

```
totalWeight = sum(weights)
raw_i       = total * weight_i / totalWeight     (integer division)
remainder   = total - sum(raw_i)
```

`remainder` แจกคนละ 1 สตางค์ ตามลำดับ **เศษที่ถูกตัดทิ้งมากที่สุดก่อน** (largest remainder method) ถ้าเศษเท่ากันให้ใช้ลำดับใน §2.4 ตัดสิน

ตัวอย่าง: 100.00 บาท, weights `[1, 1, 2]` → totalWeight 4
`raw = [2500, 2500, 5000]` รวมพอดี ไม่มีเศษ → `[2500, 2500, 5000]` ✓

ตัวอย่างที่มีเศษ: 100.00 บาท, weights `[1, 1, 1]` → `raw = [3333, 3333, 3333]`, remainder `1`
เศษที่ถูกตัดเท่ากันทั้งสามคน → ให้คนแรกตามลำดับ §2.4 → `[3334, 3333, 3333]` ✓

### 2.4 ลำดับการแจกเศษสตางค์ (deterministic)

**เรียงตาม `memberId` แบบ lexicographic ascending** ห้ามใช้ลำดับที่ผู้ใช้เห็นบนหน้าจอ หรือลำดับใน list ที่อาจเปลี่ยนตาม query

เหตุผล: ต้องได้ผลเดิมทุกครั้งที่คำนวณซ้ำบนเครื่องคนละเครื่อง ไม่งั้นสองคนเปิดบิลเดียวกันแล้วเห็นตัวเลขต่างกัน 1 สตางค์

> ผลข้างเคียงที่ยอมรับได้: คนที่ `memberId` เรียงมาก่อนจะรับเศษสตางค์บ่อยกว่าเพื่อน คิดเป็นเงินไม่เกินหลักสตางค์ต่อทริป ถ้าอยากแฟร์กว่านี้ในอนาคต ให้ใช้ `hash(expenseId + memberId)` เป็นลำดับแทน แล้วเศษจะกระจายแบบสุ่มแต่ยัง deterministic

### 2.5 `ITEMIZED` — แยกรายคน

แต่ละคนกรอกยอดของตัวเองตามที่สั่งจริง ระบบไม่ได้หารอะไรให้เลย

- `totalAmount` **ไม่ได้ให้ผู้ใช้กรอก** แต่ถูก derive จากผลรวมของ shares: `totalAmount = sum(shares)` (ใช้ `ExpenseSplitter.itemizedTotal`) — invariant ของ §2.2 (`sum(shares) == totalAmount`) จึงเป็นจริง **by construction** ไม่ต้อง validate เพิ่ม
- input ที่ว่างหรือ parse ไม่ได้ ต้องถูก **reject ที่หน้า editor** (ปิดปุ่มบันทึก + แสดง error) **ห้าม coerce เป็น 0 เงียบ ๆ** เพราะยอด 0 ที่ผู้ใช้ไม่ได้ตั้งใจจะทำให้ total เพี้ยนโดยไม่มีใครรู้ตัว
- เส้นทาง self-edit (สมาชิกแก้เฉพาะยอดของตัวเองในบิลที่มีอยู่แล้ว) ต้องคำนวณ `totalAmount` ใหม่จาก shares ทั้งชุด **ภายใน Firestore transaction เดียวกัน** กับการเขียน share ที่แก้ เพื่อกันกรณีสองเครื่องแก้พร้อมกันแล้ว total ค้างค่าเก่า

## 3. การคำนวณยอดคงเหลือ (net balance)

สำหรับสมาชิกแต่ละคน:

```
balance(m) = Σ (totalAmount ของบิลที่ m เป็นคนจ่าย)
           − Σ (share.amount ของ m ในทุกบิล)
           − Σ (settlement ที่ m เป็นผู้โอน, status = CONFIRMED)
           + Σ (settlement ที่ m เป็นผู้รับ, status = CONFIRMED)
```

- `balance > 0` = คนอื่นติดเรา (เราออกไปเกิน)
- `balance < 0` = เราติดคนอื่น

**Invariant:** `sum(balance ของทุกคน) == 0` เสมอ — ใช้เป็น assertion ในเทสต์และ log warning ใน production ถ้าไม่เป็นจริง

`settlement` ที่ยังเป็น `PENDING` **ไม่ถูกนำมาหัก** แต่ UI แสดงเป็นสถานะ "รอยืนยัน" บนรายการนั้น

## 4. Debt simplification

ลดจำนวนครั้งการโอนให้น้อยที่สุด โดยไม่สนใจว่าเดิมใครติดใคร (A ติด B, B ติด C → ให้ A โอนตรงไป C)

**Algorithm — greedy max-max matching:**

```
1. แยกสมาชิกเป็น creditors (balance > 0) และ debtors (balance < 0)
2. เรียง creditors จากมากไปน้อย, debtors จาก |balance| มากไปน้อย
   (tie-break ด้วย memberId ascending)
3. จับคู่หัวแถวทั้งสองฝั่ง: amount = min(creditor.balance, |debtor.balance|)
4. บันทึกรายการโอน debtor → creditor เป็นจำนวน amount
5. หักยอดทั้งสองฝั่ง ใครเหลือ 0 ตัดออกจากคิว
6. ทำซ้ำจนคิวว่าง
```

**ผลลัพธ์:** จำนวนรายการโอน ≤ `(จำนวนคนที่ balance ≠ 0) − 1`

> หมายเหตุทางทฤษฎี: การหาจำนวนโอนน้อยที่สุดจริง ๆ เป็นปัญหา NP-hard (subset-sum) แต่ greedy ให้ผลเท่ากับ optimal ในเกือบทุกกรณีจริงของทริปเพื่อน และให้ผลแย่กว่า optimal ได้มากสุดไม่กี่รายการ ที่ขนาด ≤ 15 คน ต่างกันไม่เกิน 1–2 ครั้งโอน ไม่คุ้มกับความซับซ้อนของ exact algorithm

**ต้อง deterministic:** ทุกคนที่เปิดหน้าสรุปยอดต้องเห็นรายการโอนชุดเดียวกันเป๊ะ ๆ ดังนั้น tie-break ด้วย `memberId` เป็นข้อบังคับ

## 6. การแสดงผล

- แสดงทศนิยม 2 ตำแหน่งเสมอ: `1,850.00`
- คั่นหลักพันด้วย comma ใช้ `NumberFormat.getCurrencyInstance(Locale("th","TH"))` หรือ formatter ที่เขียนเอง
- ยอดคงเหลือ: บวกนำหน้าด้วย `+` สีเขียว, ลบนำหน้าด้วย `−` (U+2212 ไม่ใช่ hyphen) สีแดง
- ห้ามแสดงยอดที่ยังไม่ผ่าน `Money.format()`

## 7. PromptPay QR

สร้าง payload EMVCo ฝั่ง client ไม่ต้องเรียก API ภายนอก

- Merchant ID `A000000677010111` (PromptPay)
- Proxy: เบอร์มือถือ (13 หลัก `0066` + เบอร์ตัดศูนย์หน้า) หรือเลขบัตรประชาชน 13 หลัก
- Amount tag `54` ใส่ทศนิยม 2 ตำแหน่ง
- ปิดท้ายด้วย CRC-16/CCITT-FALSE tag `63`

แนะนำ library: `com.github.kittinunf:promptpay-qr` หรือเขียนเอง ~80 บรรทัด (payload spec เป็นมาตรฐานเปิด) แล้ว render เป็นภาพด้วย ZXing

**ต้องทดสอบด้วยแอปธนาคารจริงอย่างน้อย 2 แอปก่อน release** — QR ที่ format ผิดจะสแกนได้แต่โอนไม่ได้ ซึ่งเป็น bug ที่ผู้ใช้เจอตอนกำลังจะจ่ายเงินพอดี
